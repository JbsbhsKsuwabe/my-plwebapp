SEC. 1

Introdução

1.1 Propósito do Documento

Este documento constitui a Documentação de Engenharia de Software do sistema "Tem Luz Aí?", desenvolvido como parte do projeto de pesquisa científica CientificAção, vinculado ao Instituto Federal da Bahia (IFBA). O documento tem por objetivo registrar formalmente todos os artefatos de engenharia produzidos ao longo do ciclo de vida do software, desde a elicitação de requisitos até a implantação em ambiente de produção.

Seguindo os fundamentos estabelecidos por Sommerville (2011) e Pressman (2016), a documentação cobre as etapas de análise de requisitos, modelagem, projeto de software, construção e implantação, provendo uma visão técnica abrangente que permite a manutenção, evolução e auditoria futura do sistema.

Audiência-alvo: este documento destina-se a desenvolvedores, orientadores, avaliadores de projetos de pesquisa e qualquer parte interessada que necessite compreender a arquitetura, as decisões técnicas e o processo de engenharia do sistema.

1.2 Escopo do Projeto

O sistema "Tem Luz Aí?" é um site educacional público sobre Poluição Luminosa (PL), concebido como ferramenta de divulgação científica e engajamento da comunidade escolar e do público geral. O projeto está inserido no programa CientificAção do IFBA, sob orientação da Universidade Federal da Bahia (UFBA).

O escopo funcional do sistema abrange:

  • Disponibilização de 7 módulos de conteúdo educacional sobre Poluição Luminosa, cada um com texto principal, glossário técnico, exemplos práticos, mini-revisão e quiz interativo.
  • Quiz Geral com 20 questões cobrindo os 7 módulos.
  • Rastreamento de progresso do usuário por módulo, persisitido localmente no browser.
  • Desafio Fotográfico do Céu Noturno com tutorial de fotografia noturna e envio por formulário externo.
  • Materiais para professores com conteúdo didático e orientações pedagógicas.
  • Formulários de pesquisa para professores e público geral (externos, via Google Forms).
  • SEO completo para indexação pelo Google (robots.txt, sitemap.xml, metadados, Schema.org).

O sistema não possui backend persistente próprio, banco de dados remoto, autenticação de usuários, nem coleta de dados pessoais. Toda a persistência de estado do usuário é realizada exclusivamente no localStorage do browser.

SEC. 2

Captura de Requisitos

2.1 Elicitação de Requisitos

A elicitação de requisitos do sistema "Tem Luz Aí?" foi conduzida por meio de três técnicas complementares, conforme recomendado pela literatura de engenharia de requisitos (Sommerville, 2011, cap. 4):

Técnicas de Elicitação Utilizadas

1. Análise de Documentos

O principal artefato de entrada foi a Apostila de Poluição Luminosa, documento de pesquisa produzido pelo próprio pesquisador Joabe Carmo de Santana no contexto do projeto CientificAção/IFBA. A apostila contém o corpus completo de conteúdo educacional sobre PL — conceitos, tipologia, impactos ambientais e sociais, leis e propostas — que foi integralmente digitalizado e estruturado como os 7 módulos do sistema.

2. Entrevistas Semiestruturadas com Professores

Professores da rede de ensino foram identificados como um dos públicos-alvo estratégicos do projeto. O site prevê a coleta de dados sobre o nível de familiaridade dos docentes com a Poluição Luminosa e a percepção deles sobre a relevância do tema no currículo escolar. Esta demanda resultou no card "Professor(a), participe da pesquisa" na Home e na rota /para-professores com materiais didáticos alinhados à BNCC.

3. Pesquisa com Público Geral

Reconhecendo que a PL afeta qualquer cidadão urbano, identificou-se a necessidade de engajar o público geral — não apenas estudantes ou professores. Isto originou o terceiro card do mural ("Você reconhece Poluição Luminosa na sua cidade?") com link para formulário de pesquisa rápida via Google Forms.

2.4 Regras de Negócio

IDDescriçãoImpacto Técnico
RN01 A progressão do usuário é exclusivamente client-side. Não existe autenticação, login ou sessão de servidor. Uso de localStorage no componente ProgressoBar.tsx e Quiz.tsx ("use client").
RN02 O conteúdo educacional deve ser baseado estritamente na Apostila PL e materiais oficiais do projeto CientificAção/IFBA. Nenhuma informação deve ser inventada ou extraída de fontes externas não validadas. Conteúdo codificado diretamente em data/modulos.ts (~102KB), mantendo a integridade científica.
RN03 Os formulários de pesquisa (professores, público geral, desafio fotográfico) são hospedados externamente no Google Forms. Os dados coletados são gerenciados fora do sistema. Implementado com links <a href="..."> para URLs Google Forms, sem iframe ou API de coleta de dados.
RN04 O site é de acesso público irrestrito, sem autenticação, paywall ou restrição regional. Cloudflare Pages sem regras de acesso. robots.txt com Allow: / para todos os crawlers.
RN05 O edge runtime do Cloudflare Workers é obrigatório para todas as páginas, proscrevendo o uso de APIs Node.js no servidor. export const runtime = 'edge' em todas as páginas. Proibição de fs, path, crypto Node.js, next/font/google.

2.5 Restrições do Projeto

Restrição de Plataforma: O sistema deve ser implantado exclusivamente no Cloudflare Pages/Workers. Qualquer dependência ou padrão de código incompatível com o edge runtime é vedado — incluindo APIs Node.js (fs, path, child_process), bibliotecas que requerem filesystem em runtime, e o módulo next/font/google.
Restrição de Build (OOM): O sandbox de desenvolvimento (~680MB de RAM disponível) é insuficiente para executar o next build seguido do @cloudflare/next-on-pages, que consome entre 600–800MB de RSS. O build deve ser executado obrigatoriamente via GitHub Actions (ubuntu-latest, 7GB RAM) com NODE_OPTIONS=--max-old-space-size=4096.
  • Framework: Next.js 15.3.0 com App Router (downgrade necessário — versão 16 incompatível com @cloudflare/next-on-pages na época do projeto).
  • Adapter: @cloudflare/next-on-pages v1.13.16 para conversão do output Vercel em Workers format.
  • APIs Externas: Apenas Google Forms para coleta de dados de pesquisa. Sem backend próprio, sem banco de dados remoto.
  • Linguagem: TypeScript 5.x com tipagem estrita. Proibição de any implícito.
  • Estilização: Tailwind CSS v4 exclusivamente (sem CSS-in-JS, sem styled-components). Fontes web carregadas via CSS system stack (font-sans).

3.2 Especificação de Casos de Uso

UC02
Realizar Quiz de Módulo
AtoresEstudante, Professor
Pré-condiçãoUsuário está na página /modulos/[slug]; componente Quiz renderizado.
Pós-condiçãoScore salvo em localStorage["tem_luz_ai_progresso"][quiz_modulo_N] com score, total e data ISO 8601.
Fluxo Principal
  1. Sistema exibe questão 1 de N com enunciado, alternativas e barra de progresso superior.
  2. Usuário seleciona uma alternativa (múltipla escolha) ou botão Verdadeiro/Falso.
  3. handleResposta() atualiza estado respostas[questao.id].
  4. Usuário clica "Próxima →" — questaoAtual incrementa.
  5. Passos 2–4 repetem-se para as N questões do módulo.
  6. Na última questão, botão "✅ Finalizar Quiz" fica disponível (apenas quando todas respondidas).
  7. Usuário clica "Finalizar Quiz" → handleEnviar() chamado.
  8. calcularScore() conta respostas corretas. Estado enviado = true, modoRevisao = true.
  9. Sistema persiste progresso no localStorage.
  10. Sistema exibe painel de resultado (score/total, percentual, feedback textual) + revisão de todas as questões com gabarito colorido e explicação.
Fluxo AlternativoUsuário usa o mini-índice de questões (botões numerados na base do quiz) para navegar não-linearmente. Questões respondidas ficam marcadas em verde, questão atual em azul.
RegrasRN01 (progresso client-side), RN02 (questões da apostila)
UC04
Visualizar Progresso
AtoresEstudante, Professor
Pré-condiçãoUsuário completou ao menos um quiz. Componente ProgressoBar montado na sidebar da Home.
Pós-condiçãoBarra de progresso exibida com percentual calculado e grid de módulos com scores.
Fluxo Principal
  1. Componente ProgressoBar monta no cliente (após hydration).
  2. useEffect lê localStorage.getItem("tem_luz_ai_progresso").
  3. Estado progresso atualizado (JSON parseado ou objeto vazio).
  4. Sistema calcula: completos = quizzesCompletos + (quizGeralFeito ? 1 : 0).
  5. Percentual: Math.round((completos / 8) * 100) (7 módulos + 1 quiz geral).
  6. Sistema renderiza barra de progresso gradiente (indigo→purple) na largura do percentual.
  7. Grid 4 colunas exibe células M1–M7 + Geral, coloridas por status (verde=feito, cinza=pendente).
  8. Hover em cada célula exibe tooltip com título do módulo.
ObservaçãoAntes do useEffect executar, estado é null — componente retorna null (nenhum HTML) para evitar mismatch de hydration SSR/CSR.
UC09
Indexar Conteúdo (Googlebot)
AtorGooglebot (crawler automatizado)
Pré-condiçãoSite deployed com robots.txt e sitemap.xml acessíveis em produção.
Pós-condiçãoPáginas indexadas no Google Search com snippets enriquecidos (rich results) provenientes do JSON-LD.
Fluxo Principal
  1. Googlebot requisita GET /robots.txt → recebe diretivas User-agent: * / Allow: / e URL do sitemap.
  2. Googlebot requisita GET /sitemap.xml → recebe 13 URLs com prioridades e changeFrequency.
  3. Googlebot rastreia cada URL do sitemap (5 estáticas + 7 módulos + /sitemap.xml dinâmico).
  4. Para cada página, extrai: <title>, <meta description>, canonical, Open Graph e JSON-LD.
  5. JSON-LD WebSite e EducationalOrganization processados para rich results.
  6. Conteúdo indexado no Google Search disponível para usuários buscando por "poluição luminosa", "céu noturno", "IFBA CientificAção" etc.
RegrasRN04 (acesso público), RF11 (robots.txt), RF10 (sitemap), RF12 (metadados)

// Interface principal de módulo
export interface Modulo {
  id:                  number;        // 1–7

  titulo:              string;        // Título do módulo

  icone:               string;        // Emoji representativo

  resumo:              string;        // Parágrafo de introdução
  conteudo:            string;        // Texto completo em Markdown (~10–20KB por módulo)
  glossario:           GlossarioItem[];
  exemplos:            Exemplo[];
  revisao:             string[];      // Pontos-chave da mini-revisão
  quiz:                QuestaoQuiz[]; // 5–8 questões por módulo
  textoCompleto:       string;        // Para professores — texto expandido
  orientacoesDidaticas:string;
  perguntasRevisao:    Array<{pergunta: string; gabarito: string}>;

  id:          string;

  alternativas?:string[];            // apenas para tipo multipla_escolha
  resposta:    string | boolean;     // string para MC, boolean para VF
  explicacao:  string;
}

5.2 Decisões de Design de Código

1. Edge Runtime Obrigatório em Todas as Páginas

Cada arquivo de página (page.tsx) exporta export const runtime = 'edge'. Esta declaração instrui o Next.js e o @cloudflare/next-on-pages a compilar a rota para execução no runtime de Cloudflare Workers, que é um subconjunto das Web APIs — sem suporte a APIs Node.js (fs, path, crypto, child_process etc.).

Proibições no Edge Runtime: qualquer uso de import fs from 'fs', import path from 'path', import { ... } from 'next/font/google' ou qualquer API que dependa do sistema de arquivos do servidor resulta em erro de build ou crash silencioso em produção.

2. Substituição de Math.random() por Arrays Estáticos

O React 19 exige que Server Components sejam funções puras — com output determinístico dado o mesmo input. Math.random() viola esta regra, pois retorna valores diferentes a cada renderização, causando divergências entre o HTML gerado no servidor e a hidratação no cliente (hydration mismatch), resultando em erro em produção.

A solução adotada foi criar os arrays STARS (Home) e STARS_D (Desafio) com coordenadas pré-geradas e fixas diretamente no código-fonte. Isto preserva o efeito visual de céu estrelado sem comprometer a pureza dos componentes.

3. Rota Dinâmica de Módulos sem generateStaticParams

A rota /modulos/[id] é dinâmica — o parâmetro id recebe o slug do módulo (ex: introducao). Em Next.js, rotas dinâmicas com SSG usam generateStaticParams() para pré-gerar os paths em build time. Porém, esta função é incompatível com edge runtime — o Next.js proíbe a combinação. A solução foi remover o generateStaticParams e adicionar export const dynamic = 'force-dynamic', tornando a rota resolvida dinamicamente no edge a cada requisição.

4. Renderização Markdown com Helper Customizado

O conteúdo dos módulos é armazenado como Markdown em data/modulos.ts. Para renderizá-lo como HTML, foi criada a função renderMarkdown(text: string) em app/modulos/[id]/page.tsx. Esta função processa linha a linha, identificando cabeçalhos (##, ###), listas, blockquotes, tabelas e parágrafos, aplicando formatação bold/italic/code via regex. A decisão de não usar bibliotecas como marked ou remark foi motivada pela compatibilidade com edge runtime e pelo desejo de manter o bundle mínimo.

5. Padrão useState(null) + useEffect para Hidratação

O componente ProgressoBar precisa ler o localStorage, que está disponível apenas no browser (não no servidor/edge). Para evitar erros de hydration mismatch, o padrão adotado é: 

const [progresso, setProgresso] = useState<ProgressoData | null>(null);

useEffect(() => {
  // Executa apenas no cliente, após montagem
  const saved = localStorage.getItem("tem_luz_ai_progresso");
  setProgresso(saved ? JSON.parse(saved) : {});
}, []);

// Durante SSR/hydration: renderiza null (nenhum HTML)
if (progresso === null) return null;

Este padrão garante que o HTML do servidor seja sempre vazio para este componente, eliminando qualquer divergência com a primeira renderização do cliente.

6.2 Pipeline de Build

O build segue uma sequência de quatro etapas encadeadas, onde cada etapa depende do resultado da anterior:

  1. next build (executado internamente pelo @cloudflare/next-on-pages)
    Compila os arquivos TypeScript, processa o Tailwind CSS v4, aplica tree-shaking e gera o output Vercel em .vercel/output/. Esta etapa consome entre 600–800MB de RAM (causa do problema OOM no sandbox de desenvolvimento).
  2. npx @cloudflare/next-on-pages
    Lê o output Vercel gerado pelo Next.js e o converte para o formato aceito pelo Cloudflare Workers: funções edge em .vercel/output/static/_worker.js/ e assets estáticos servíveis pela CDN do Cloudflare Pages.
  3. node scripts/fix-cloudflare-routes.mjs
    Inspeciona o arquivo _worker.js/index.js gerado para verificar se o mapeamento da rota "/" aponta para a função index.func.js (correto) ou para o asset favicon.ico (bug). Em caso de bug, realiza a correção automaticamente. Esta etapa é uma salvaguarda pós-build.
  4. wrangler pages deploy .vercel/output/static --project-name=tem-luz-ai
    Faz o upload do output para o Cloudflare Pages. O wrangler autentica via CLOUDFLARE_API_TOKEN, cria uma nova implantação no projeto "tem-luz-ai" e, após a conclusão, a nova versão entra em produção automaticamente em todos os 200+ PoPs da Cloudflare.

# Problema Causa Raiz Impacto Solução
P1 @cloudflare/next-on-pages rejeitou Next.js 16 O adapter suportava apenas Next.js ≤15.5.2 na época do projeto. A API interna do Next.js 16 havia mudado. Build falhou completamente — bloqueou todo o desenvolvimento. Downgrade para Next.js 15.3.0 via package.json. Versão estável e totalmente compatível com o adapter.
P2 Rota "/" servia favicon.ico (Content-Type: image/x-icon) em vez do HTML da Home O @cloudflare/next-on-pages, ao encontrar app/favicon.ico, registrava-o como asset estático e sobrescrevia o mapeamento da rota "/" no _worker.js/index.js com o path do favicon, em vez da função index. A Home page era completamente inacessível — todos os usuários que acessavam a raiz do site recebiam o ícone binário. Bug de severidade crítica afetando 100% das visitas. Mover app/favicon.ico para public/favicon.ico. Criação de scripts/fix-cloudflare-routes.mjs como salvaguarda que detecta e corrige o mapeamento pós-build caso o bug reapareça.
P3 generateStaticParams incompatível com edge runtime O Next.js proíbe a combinação de geração estática (generateStaticParams) com edge runtime na mesma página. Erro de build TypeScript. A rota de módulo não era compilada. Remoção de generateStaticParams. Adição de export const dynamic = 'force-dynamic'. A rota passou a ser resolvida dinamicamente no edge.
P4 Math.random() em Server Components Função impura viola a regra de pureza dos Server Components React 19. Produz valores diferentes no servidor e no cliente, causando hydration mismatch. Erro de runtime no browser: "Hydration failed because the initial UI does not match what was rendered on the server." Aparecia no console em produção. Substituição por arrays STARS e STARS_D com 60 e 40 coordenadas pré-geradas, respectivamente, embutidas no código-fonte.
P5 next/font/google incompatível com edge runtime O módulo next/font/google utiliza APIs Node.js (fs) internamente para baixar e cachear fontes, o que é proibido no edge runtime. Erro de build: "The edge runtime does not support Node.js 'fs' module." Remoção completa de next/font/google. Uso de font-sans do Tailwind CSS (system font stack: Segoe UI, Arial, sans-serif) que não requer download.
P6 SIGKILL (OOM) durante next build no sandbox O sandbox de desenvolvimento disponibiliza ~680MB de RAM. O processo do worker interno do Next.js (que faz bundling paralelo) alocou até 471MB de RSS, levando o kernel Linux a matar o processo por OOM. Impossibilidade de fazer build e deploy diretamente do sandbox. Bloqueou a implantação dos arquivos SEO (Iteração 3). Criação do workflow GitHub Actions (.github/workflows/deploy.yml) com ubuntu-latest (7GB RAM) e NODE_OPTIONS=--max-old-space-size=4096. Adição de outputFileTracingExcludes no next.config.ts para reduzir o file tracing.
P7 git push bloqueado para .github/workflows/ O token do GitHub App utilizado pelo sandbox não possuía a permissão workflows (escopo necessário para criar/modificar arquivos em .github/workflows/). Impossibilidade de fazer push automático do arquivo deploy.yml. O CI/CD não pôde ser ativado automaticamente. O arquivo foi commitado localmente no repositório. Para ativá-lo, é necessário adicionar o arquivo manualmente via interface web do GitHub (Actions → New workflow) ou via push com um token com permissão workflows.
